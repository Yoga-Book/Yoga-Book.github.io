= Hardware support boundaries
:description: Device scope, subsystem ownership, constraints, and evidence requirements for Yoga Book Linux.

Yoga Book Linux is an integration effort, not a single driver.
A working system combines a device-specific kernel, firmware and topology, userspace services, desktop integration, packaging, and physical validation.

Last reviewed:: 2026-10-12

== Supported-device boundary

The primary integration and physical-acceptance target is the Lenovo Yoga Book **YB1-X91L**.

Do not assume that an artifact validated on YB1-X91L is safe or functional on YB1-X90F, YB1-X90L, YB1-X91F, or another Yoga Book generation.
Model-specific support must be stated by the project that owns the artifact and backed by evidence from that exact model.

[IMPORTANT]
====
The Ubuntu production autoinstaller is intentionally restricted to the exact DMI identity `Lenovo YB1-X91L` and the `CJNB4R` internal eMMC topology.
It is not a generic Yoga Book installer.
====

== Cross-system constraints

Secure Boot:: The Yoga Book kernel is unsigned, so Secure Boot must be disabled.

Recovery kernel:: Keep a known-good distribution kernel installed and bootable until the Yoga Book kernel passes the required checks.

GNSS firmware:: The open package cannot redistribute Lenovo, Broadcom, or Android binaries. The user must supply and import the exact private runtime described by the GNSS project.

Camera maturity:: Both sensors have transport and device-side evidence, but the camera stack remains experimental. Final image quality, browser behavior, switching, thermals, and kernel compatibility require release-specific physical acceptance.

Conditional hardware:: LTE, GNSS sky/fix, Micro-HDMI, headset, USB accessories, and SD media cannot be fully accepted when their prerequisite is absent.

== What a support claim means

[cols="1,3",options="header"]
|===
|Claim |Required interpretation

|Implemented
|Code or configuration exists for the subsystem. It may not build, install, or operate on the tablet.

|Packaged
|An installable artifact exists. Packaging alone does not prove runtime behavior.

|Structurally validated
|Identity, driver, topology, package, or service state matches the stated expectation.

|Functionally validated
|A bounded operation or state transition completed and cleanup was checked.

|Physically accepted
|A person observed the stated behavior on the named hardware with recorded artifacts and environment.

|Recovery-ready
|The complete release-specific installation, recovery, and physical-acceptance procedure passed with preserved evidence.
|===

See xref:support-status.adoc[Support and evidence] for evidence semantics and xref:validation.adoc[System validation] for the practical workflow.
